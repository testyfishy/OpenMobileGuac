# OpenMobileGuac — Delivery Plan

Companion to [SPEC.md](SPEC.md). Requirement IDs (SRV-1, PTR-2, …) refer to SPEC §6.

## How to use this plan

Each task below is a self-contained brief meant to be run by a fresh Opus session:

1. Switch the session model to Opus.
2. Prompt: `Read docs/SPEC.md and docs/PLAN.md, then do task T1.3. Follow the working rules.`
3. When the session reports done, the owner ticks the task's box here and commits. Sessions
   report; they do not edit this file.

Tasks marked **U** need the project owner in person (accounts, real devices, decisions).
Tasks inside a phase can run in parallel unless "Depends" says otherwise; two sessions must
not edit the same files at once.

### Working rules for every task

- Read the SPEC sections the task cites before writing code.
- Do not write Guacamole REST paths, tunnel parameters, or library class/method names from
  memory. Read them from the vendored library or from `apache/guacamole-client` at tag
  `1.6.0` (`gh api repos/apache/guacamole-client/contents/<path>?ref=1.6.0`).
- No code or assets from PocketGuac (closed source, unlicensed).
- `PointerModel`, `KeyModel`, `Viewport`, and the gesture recogniser stay free of DOM and
  Capacitor imports and ship with unit tests.
- All network access goes through `HttpClient` / `SessionTransport`.
- This repo is public. Recorded instruction streams, screenshots, and fixtures may only be
  captured from a clean throwaway remote desktop with nothing personal on screen, and the
  owner reviews them before commit. No real hostnames, IPs, or usernames in docs or fixtures.
- Never commit credentials. The dev server URL and test account live in `app/.env.local`
  (git-ignored).
- A task is done only when its "Done when" holds and `npm run check` (typecheck + lint +
  unit tests + build) passes in `/app`. If something could not be verified (most often: iOS
  on a device), say so in the report and add it to the relevant device checklist rather than
  claiming it works.
- New dependencies must be Apache-2.0/MIT/BSD-compatible; record them in `NOTICE`.

### Environment facts (dev PC, checked 2026-11-18)

Windows 11; Node, Git, GitHub CLI, and JDK 21 installed. **Not** installed: Docker, Flutter.
Android SDK presence not yet checked. No Mac (assumed).

## Phase 0 — Foundations and feasibility gate

Goal: prove the architecture in SPEC §8.1 on real devices before investing in features.

- [ ] **T0.1 Repo scaffold.**
  Init git; add `LICENSE` (Apache-2.0), `NOTICE`, `README.md` (what it is, status, unofficial
  disclaimer), `.gitignore`, `CONTRIBUTING.md`. Create `/app` with Vite + React + TypeScript
  (strict), ESLint, Prettier, Vitest, and an `npm run check` script. Add Capacitor (current
  stable; confirm the version and its minimum iOS/Android from the official docs) and
  generate the `android` project. Add `app/.env.example` with `VITE_DEV_GUAC_URL`,
  `VITE_DEV_GUAC_USER`, `VITE_DEV_GUAC_PASS`. Report whether the Android SDK is installed and
  what is missing.
  *Done when:* `npm run check` passes; `npm run dev` serves a placeholder screen.

- [ ] **T0.2 Vendor the Guacamole client library.** Depends: T0.1.
  Fetch `guacamole-common-js/src/main/webapp/modules/*.js` from `apache/guacamole-client` at
  tag `1.6.0` into `app/src/vendor/guacamole-common-js/`, with upstream `LICENSE`/`NOTICE`
  and a `README` recording the tag and commit. Expose it as an ES module with TypeScript
  declarations for the parts we use (Client, Display, Tunnel classes, Keyboard, Mouse, Touch,
  Status, stream readers/writers). Add a script `scripts/update-guac.mjs` that re-vendors
  from a given tag.
  *Done when:* a unit test imports the module and parses a sample instruction with its
  parser; build passes.
  *Optional sub-task:* document in `docs/dev-server.md` how to run a disposable local
  Guacamole stack with Docker Desktop, for contributors who have it.

- [ ] **T0.3 Core interfaces.** Depends: T0.1.
  Define in `app/src/core/`: `HttpClient` (with `FetchHttpClient` and `NativeHttpClient`
  implementations), `SessionTransport` (wrapping a library tunnel; with `WebSocketTransport`
  and a `ReplayTransport` that plays a recorded instruction file), `SecureStore`, and typed
  models for server profile, auth token, connection, connection group. Platform selection in
  one place.
  *Done when:* unit tests cover `ReplayTransport` and model parsing.

- [ ] **T0.4 Spike: log in and show a desktop.** Depends: T0.2, T0.3, U1.
  Minimal and throwaway-quality UI is fine. Read the 1.6.0 web client source (SPEC §8.3) to
  establish the real login request, connection-tree request, and tunnel connect parameters;
  write what you find to `docs/protocol-notes.md` with file references. Implement login →
  list connections → open one → render it with the library's default mouse handling. In
  browser dev mode, route through a Vite dev proxy. Record a short instruction stream to
  `app/test/fixtures/` for `ReplayTransport`.
  *Done when:* in a desktop browser against the owner's server, a remote desktop is visible
  and clickable; `docs/protocol-notes.md` exists.

- [ ] **T0.5 Spike: keyboard and clipboard prototypes.** Depends: T0.4.
  Prototype `TextInputBridge` (SPEC §8.4) and a Paste button that reads the device clipboard
  and sends it to the remote, plus remote → device clipboard. Read the library's
  `Keyboard.js`, `OnScreenKeyboard.js`, and the web client's text-input mode first.
  Desktop emulation types with a hardware keyboard and so proves little. Also serve the dev
  build on the tailnet (`vite --host`) and write `docs/checklists/phase0-browser.md` for the
  owner to run in iPhone Safari and Android Chrome: keyboard raise, letters, backspace,
  enter, swipe typing/IME. Establish whether clipboard access works there over plain `http`
  (it may require a secure context); if not, say so and leave clipboard to G0.
  *Done when:* typing and both clipboard directions work in a desktop browser against the
  dev server, and the owner has run the phone-browser checklist with results recorded.

- [ ] **T0.6 Device builds and CI.** Depends: T0.4.
  Android: debug APK builds locally (if the SDK is present) and in GitHub Actions; cleartext
  and mixed-content settings so `http://`/`ws://` servers work. iOS: generate the `ios`
  project; a GitHub Actions macOS workflow that builds an unsigned simulator build now and a
  signed TestFlight build once U2a provides signing secrets (document the required secrets in
  `docs/release.md`). Add the ATS exception and usage-description strings.
  *Done when:* CI is green for Android APK and iOS simulator build; APK artifact downloadable.

- [ ] **U-gate G0. Feasibility check on real devices.** Depends: T0.5, T0.6.
  Owner installs the Android APK (and the TestFlight build when signing exists) and runs
  `docs/checklists/phase0.md`, which T0.6 writes. **Pass criteria:**
  1. Login and connection list work against the tailnet server over `http://`.
  2. A session displays and stays connected for 10 minutes.
  3. Soft keyboard rises on demand; letters, backspace, enter arrive correctly.
  4. Phone → remote paste and remote → phone copy both work.
  5. Pinch zoom of the display is smooth.

  If 1 or 2 fail: do **T0.7 Native tunnel/HTTP bridge** (a small Capacitor plugin
  implementing `SessionTransport` over a native WebSocket) and re-test. If 3 fails on iOS
  with no workaround, or 5 fails badly, stop and revisit SPEC §8.1 before Phase 1.

## Phase 1 — First-class session MVP (all P1 requirements)

- [ ] **T1.1 Design system and navigation.** App shell, routing, theme (system/light/dark),
  safe areas, base components, icon set, string table. A11Y-1 for chrome.
  *Done when:* empty screens for Servers, Connections, Session, Settings navigate correctly
  at phone and tablet widths.

- [ ] **T1.2 Servers and login.** Depends: T1.1. SRV-1…SRV-5.
  Profile CRUD, URL normalisation and error taxonomy, secure storage plugin, token reuse and
  silent re-login, generic additional-credentials form (TOTP).
  *Done when:* unit tests for URL normalisation and auth state machine; manual login works
  in browser dev mode, including the expired-token path.

- [ ] **T1.3 Connection browser.** Depends: T1.2. CON-1…CON-3.
  *Done when:* tree, search, refresh, recents, favourites work against the dev server; tree
  parsing is unit-tested from a captured fixture.

- [ ] **T1.4 Viewport.** Depends: T0.3. DSP-1, DSP-2, DSP-5 (maths only).
  Pure module: fit modes, zoom/pan with bounds and momentum, remote↔screen coordinate
  mapping, keyboard inset, follow-pointer.
  *Done when:* unit tests cover every fit mode in portrait and landscape, bounds, and
  follow-pointer with a keyboard inset.

- [ ] **T1.5 Gesture recogniser and PointerModel.** Depends: T1.4. PTR-1, PTR-2.
  Pure modules: Pointer Events in → gestures (tap, double tap, long press, drag, two/three
  finger tap, two-finger drag, pinch) → remote mouse state per mode. Tunable thresholds.
  *Done when:* table-driven unit tests cover every gesture row of PTR-1 and PTR-2, including
  ambiguous sequences (tap vs. drag start, two-finger tap vs. pinch).

- [ ] **T1.6 Session screen.** Depends: T1.3, T1.4, T1.5. DSP-1…DSP-7, DSP-9 (basic),
  PTR-3, PTR-4.
  Replace the spike: `RemoteDisplay`, `GestureLayer`, compositor-transform zoom, cursor
  rendering, session toolbar (view mode, pointer mode, keyboard, paste, combos, disconnect),
  rotation/resize handling, "Match device" resize, keep-awake, haptics, connection-state UI.
  *Done when:* S1 and S4 pass in a desktop browser with touch emulation; a replay-transport
  test renders a fixture to the display.

- [ ] **T1.7 Keyboard, key bar, combos.** Depends: T1.6. KEY-1…KEY-5.
  Production `TextInputBridge` and pure `KeyModel` (keysym mapping, sticky/locked modifiers,
  combo sequencing), key bar, combo menu with presets and saved custom combos.
  *Done when:* unit tests for `KeyModel` (modifiers, combos, Unicode → keysym); typing and
  combos work in browser dev mode and in the owner's phone browsers via the tailnet dev URL; `docs/checklists/keyboard.md` written for device testing.

- [ ] **T1.8 Clipboard.** Depends: T1.6. CLP-1…CLP-4.
  *Done when:* both directions and "type clipboard" work in browser dev mode; device
  checklist items added.

- [ ] **T1.9 Settings.** Depends: T1.1. SET-1, per-connection remembered modes.

- [ ] **U-gate G1. MVP device pass.** Owner runs `docs/checklists/mvp.md` (assembled from
  the task checklists) on an iPhone, an Android phone, and a foldable if available. Defects
  become tasks **T1.x-fix**. Phase 2 starts when scenarios S1–S4 pass on both platforms.

## Phase 3 — Release engineering and store submission

Can start as soon as G1 passes; does not need Phase 2 to finish.

- [ ] **T3.1 Signed release pipeline.** Depends: U2a, U2b. Tag-driven CI: Android AAB to Play
  internal track + APK to GitHub Releases; iOS IPA to TestFlight. Versioning, changelog,
  `docs/release.md`.
- [ ] **T3.2 Demo mode** (and optional public demo server). Depends: U5. SPEC §10.3.
  *Done when:* a fresh install can open "Demo server" offline and exercise every session
  control.
- [ ] **T3.3 Compliance research and documents.** Verify each item in SPEC §10.2 against the
  current official Apple, Google, and ASF pages and record findings with links in
  `docs/store-compliance.md`. Write `docs/privacy-policy.md` and publish it via GitHub Pages.
  Draft the ATS justification and review notes.
- [ ] **T3.4 Store listings.** Depends: U3. Name, icon, descriptions, screenshots for the
  required device sizes (generated from demo mode), feature graphic, data-safety and
  privacy-label answers. Text in `docs/store/`.
- [ ] **U6. Beta.** Owner recruits testers (Play closed testing as required; TestFlight
  external group), collects feedback for the required period.
- [ ] **U7. Submit.** Owner submits to both stores, answers review questions. Rejections
  become tasks.

## Phase 4 — Launch and after

- [ ] **T4.1 Launch housekeeping.** Issue templates, security policy, contribution guide
  polish, F-Droid metadata, announcement post for the Guacamole user mailing list.
- [ ] **T4.2 Backlog triage.** P3 items (SRV-9, CON-6), profiling to decide whether a native
  rendering core is warranted, community translations.
